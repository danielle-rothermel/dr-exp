## Defect status

### D-2 — closed

`dr_exp retry` no longer bottoms out in a confusing "no failed stage" error on a
cancelled item. It detects the CANCELLED stage explicitly and raises a
`click.ClickException` carrying the operator message
(`src/dr_exp/cli/main.py:497-513`, message template at
`src/dr_exp/cli/main.py:50-63`), so the exit code is 1 and there is no
traceback. Assertions 18–20 above are the live evidence; the CLI behaviour is
pinned by the integration tests added in the same commit
(`tests/integration/test_lifecycle.py`).

The decision this encodes is that cancellation is terminal in dr-platform's
ledger and dr-exp does not fight that. The operator's route back to the work is
a new campaign, and the resume is real rather than nominal: assertions 21–29
show a new work item's *first* attempt picking up at round 1 epoch 2 and
finishing the job.

### D-3 — closed

`MachineProfile.workspace_for(campaign_key, work_key)` returns
`workspace_root/runs/<campaign_key>/<work_key>/`
(`src/dr_exp/config/machine.py:120-131`); the attempt number stays in
`request["attempt"]` and in the records but no longer selects a directory
(`src/dr_exp/execution/attempt.py`, `src/dr_exp/platform/pipeline.py`). Unit
coverage: `tests/unit/test_machine.py` (two campaigns sharing a `work_key` get
distinct workspaces; two attempts of one work item share one),
`tests/unit/test_attempt.py`, `tests/unit/test_pipeline.py`.

Two consequences are now observed rather than argued. A checkpoint written by
one attempt is visible to the next attempt of the same work item — V4 already
depended on this for crash recovery and it still holds, since recovery reuses
attempt 1's workspace. And the cross-campaign collision that forced V3's
"Incident 0" is gone: `val-v3b` and `val-v3c` ran the identical config, produced
the identical `work_key`, and never touched each other's files.

### Not closed — DBOS cancellation log noise

V3 noted `DBOSWorkflowCancelledError`, `DBOSAwaitedWorkflowCancelledError`, and
one `asyncio: Future exception was never retrieved` in the worker log at cancel
time. Track C authorised a fix only if a one-line asyncio result-retrieval
change in `platform/pipeline.py` removed it without changing behaviour. It does
not, so the noise is unchanged here: `val-v3b/worker.log:344-368` carries the
same three, in the same order, at 17:02:52–17:02:53.

The unretrieved future is not one dr-exp creates. It is the
`concurrent.futures.Future` that `asyncio.to_thread` builds inside
`dbos/_outcome.py:211` (reached from `dbos/_core.py:677`), which completes with
`DBOSAwaitedWorkflowCancelledError`; nothing in dr-exp holds a reference to it,
so no dr-exp-side `await` or `.exception()` call can retrieve it. dr-exp's own
`attempt_task` *is* retrieved on the normal path — `wait_for(shield(...))`
returns its result at `src/dr_exp/platform/pipeline.py:108-111`. A fix belongs
in DBOS, or nowhere.

The outcome remains correct in every place that records state: the ledger
(assertion 11), DBOS status (13), and the run record (14) all say *cancelled*,
never *failed*. Noisy, not wrong — recorded, still not filed as a dr-exp defect.

epoch rather than as nothing at all.

## Verdict

**pass.** V3's cancellation half is reproduced exactly, and V3's resume half —
the half that failed — now completes: `retry` refuses a cancelled item with a
message that tells the operator what to do, the prescribed new-campaign path
produces a genuinely new work item, and that item's first attempt resumes from
the cancelled campaign's checkpoint and finishes SUCCEEDED with round 0's
history intact. D-2 and D-3 are closed. The DBOS cancellation log noise is
unchanged and has no dr-exp-side fix.
