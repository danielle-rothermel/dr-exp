# V4 — worker shutdown and recovery (machine `mini`, 2026-08-21)

Validation V4 of `docs/plans/validate-with-dr-vision.md`: two real dr-vision
jobs in flight, SIGTERM to the worker, then a restarted worker with the same
`executor_id` recovering both attempts and resuming each from its checkpoint.

Result: **pass** — all 21 assertions verified state-based. Both children were
torn down inside the grace after checkpointing, both work items stayed
`admitted` (never terminal, never FAILED), the restarted worker recovered both
DBOS workflows, and each resumed at exactly its checkpoint epoch with **zero
recomputed epochs** before finishing SUCCEEDED.

V4 also **narrows defect D-3** as recorded in V3. V3 predicted that DBOS
recovery would hand the recovered attempt a fresh empty `attempt-2/` and so
silently restart from scratch. That is not what recovery does: DBOS re-runs the
*same* workflow with the *same* `attempt_number`, so the workspace is the same
directory and the checkpoint is found. D-3 is real but is confined to paths that
*increment* the attempt number (`dr_exp retry`), not to recovery. The correction
is written up under "Bearing on D-3" below; no new defect was found.

### Incident 0 — workspaces cleared before the run

Both configs produce the same `work_key` in every campaign and attempt
workspaces are keyed by `work_key` alone (`src/dr_exp/config/machine.py:121-123`),
so V1/V2/V3 artifacts were already in both `attempt-1/` directories
(random: V3's `checkpoint.pt` + `metrics.jsonl`; shrink-perturb: V2's
`result.json`, `rounds.json`, `metrics.jsonl`). Starting V4 on top of them would
have made every resume assertion ambiguous — in particular a pre-existing
`checkpoint.pt` would have been picked up as a spurious resume source. Both
directories were archived to
`~/drotherm/data/dr-exp/validation-logs/val-v4/preexisting-workspaces/` and
removed before submitting. Same cross-campaign workspace sharing V2 and V3
already recorded; provenance, not a new defect.

### Deviation: the SIGTERM gate, and `--max-jobs 2` on the restart

The assignment says to SIGTERM "once both are ADMITTED and have written a
checkpoint". **A running dr-vision job never has a checkpoint on disk.**
`checkpoint.pt` is written only on the stop path: `run_warm_start` calls
`save_state` solely in the `outcome.record is None` branch, i.e. when a round was
interrupted (`dr-vision/src/dr_vision/runner.py:261-266`), and `entry/train.py:96-111`
passes `save_state` only for that purpose. Waiting for a checkpoint before the
SIGTERM would therefore have deadlocked. The gate used instead is the V3 gate —
poll each `metrics.jsonl` until it holds a `kind: "round"` record, so each job is
demonstrably past a checkpointable position — and the checkpoints are written
*by* the SIGTERM, which is what assertion 6 verifies. Confirmed state-based:
assertion 5 records that neither `checkpoint.pt` existed at the instant before
the signal.

The restart used `--max-jobs 2` so the worker reaches a terminal state on its own
once both items finish, rather than needing a second operator SIGTERM. This does
not weaken any assertion: recovery happens at worker launch, long before the
limit is consulted.

## Bearing on D-3 (recorded in V3)

V3 filed **D-3** — "the per-attempt workspace makes the documented resume
contract unachievable" — and predicted that V4 would demonstrate it:

> DBOS recovery re-runs the stage body as attempt *n+1*, which likewise gets a
> fresh empty directory, so a recovered attempt silently restarts from scratch
> rather than resuming. V4 exercises exactly that path and should be expected to
> show it.

**That prediction is wrong, and V4 is the counter-evidence.** DBOS recovery does
not create attempt *n+1*. It re-executes the *same* workflow, and the attempt
number handed to the trainer comes from that workflow's own admission payload —
`src/dr_exp/platform/pipeline.py:124-127`:

```python
    request = AttemptRequest(
        work_key=payload.work_key.value,
        attempt=payload.attempt_number,
        config=config,
    )
```

`payload` is the `AdmissionPayload` recorded when the workflow was admitted, so
`attempt_number` is still 1 after recovery. `workspace_for(work_key, 1)`
(`src/dr_exp/config/machine.py:121-123`) therefore returns the same directory,
the checkpoint written during shutdown is right where `_resume_checkpoint` looks
for it, and the resume works. Assertion 15 confirms the mechanism directly:
`current_attempt` stayed 1, exactly one `platform_stage_attempts` row exists per
work item, no `attempt-2/` was ever created, and `recovery_attempts` incremented
on the same `workflow_uuid`.

So the at-least-once recovery half of the README's contract
(`README.md:138-144`) **is** satisfied end to end, including checkpoint-resume.
D-3's remaining scope is narrower than V3 stated: it bites only where the
attempt number actually increments, which today is `dr_exp retry` — the FAILED
path, and (were D-2 fixed to allow it) the cancelled path. V3's assertion 20 is
still correct on its own terms: a *retried* attempt 2 would get an empty
`attempt-2/`. But "a recovered attempt silently restarts from scratch" is not
true and should not be carried forward.

This does not close D-3 — the retry path remains genuinely broken and the
contract question V3 raised (per-`work_key` durable directory vs. dropping the
resume language) is still open. It changes D-3's severity and its evidence:
recovery is not affected, so the decision only has to cover retry.

## Throughput observations

Per-epoch seconds from the `kind: "epoch"` records in `metrics.jsonl`. Both jobs
ran **2-wide** on the GPU for the whole validation (`worker_concurrency: 2`, two
children throughout), so every number here is the 2-wide figure — directly
comparable to V2's 2-wide numbers and roughly 2.8x V1/V3's solo baseline.

| Job | Round | Subset | Phase | n | First (s) | Min | Median | Mean | Max | Total (s) |
|---|---|---|---|---|---|---|---|---|---|---|
| random | 0 | 16666 | pre-SIGTERM | 22 | 4.31 | 3.62 | 3.96 | 4.26 | 5.57 | 93.8 |
| random | 1 | 33333 | pre-SIGTERM | 5 | 11.47 | 7.31 | 11.31 | 10.21 | 13.02 | 51.0 |
| random | 1 | 33333 | post-recovery | 28 | 9.33 | 7.09 | 8.70 | 8.27 | 9.33 | 231.7 |

- Totals: random 55 epochs / 376.5 s of epoch time; shrink-perturb 58 epochs /
  378.9 s. Both jobs' round-1 post-recovery medians are 8.70 s and their means
  agree to 0.01 s (8.27 vs. 8.26) — the two concurrent jobs share the GPU almost
  exactly evenly, the same symmetry V2 observed.
- **2-wide cost, and a discrepancy with V2.** Round 0 at 16666 samples: median
  3.96 s (random) and 4.31 s (shrink-perturb) against V1's 3.02 s and V3's
  3.16 s solo — about 1.3x. Round 1 at 33333 samples: median 8.70 s for both
  jobs against V1's 6.11 s and V2 arm A's 6.10 s solo — **1.42x**. That is a
  42% per-epoch slowdown at 2-wide, noticeably worse than the 20–23% V2
  measured for its 2-wide arms (7.50 and 7.35 s/epoch at the same 33333-sample
  subset). Both validations used `worker_concurrency: 2` on the same profile
  and the same two-round shape, so the numbers should be comparable and are
  not. Two candidate explanations, neither verified here: V2's 2-wide arms
  overlapped a third arm's start/finish so only part of their round-1 window
  was genuinely contended, whereas V4's two jobs were contended for their
  entire round 1; or the machine was under different external load. **This is
  an open throughput question, not a dr-exp defect** — every V4 correctness
  assertion is unaffected. It matters only for the concurrency decision the
  throughput study has to make, and it means `mini`'s 2-wide penalty should be
  treated as a range (20–42%) rather than V2's single figure until V6 adds a
  third measurement. Even at 42%, 2-wide is still a makespan win (1.42x
  per-epoch cost for 2x aggregate work ≈ 1.4x throughput).
- **Recovery is not a throughput event.** Post-recovery epochs are *faster* than
  the pre-SIGTERM round-1 epochs (median 8.70 s vs. 11.31 s for random), because
  the pre-SIGTERM window overlapped the other job's round-0/round-1 transition
  and its evaluation passes. There is no restart penalty visible in the per-epoch
  series, and no epoch is recomputed (assertion 17), so the only cost of the
  interruption is the checkpoint write plus process startup.
- **Checkpoint cost under load.** Two children each serialized an 8.6 MB
  checkpoint concurrently and both were gone on the first poll after the signal,
  inside the 30 s grace. Consistent with V3's single-job finding; the grace has
  ample headroom at this model size even 2-wide.
- **Accounting note (not a defect).** A round record's `seconds` covers only the
  wall time of the process that *closed* the round, so round 1's 231.7 s (random)
  excludes the 51.0 s spent on its first 5 epochs before the SIGTERM, while its
  `epochs: 33` counts all of them. Anyone deriving per-epoch cost from
  `rounds.json` alone across an interrupted run will understate it; the
  per-epoch records in `metrics.jsonl` are the accurate source. Worth knowing
  before the throughput study consumes these files.
