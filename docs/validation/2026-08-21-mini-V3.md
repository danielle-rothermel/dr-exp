# V3 — cancel and resume (machine `mini`, 2026-08-21)

Validation V3 of `docs/plans/validate-with-dr-vision.md`: cancel a real
dr-vision job mid-round, then retry it and confirm the new attempt resumes
from the checkpoint.

Result: **fail** — on dr-exp, and on the half of V3 that dr-exp owns.

The cancellation half passed completely and cleanly: SIGTERM reached the
child, dr-vision checkpointed inside the 30 s grace, the child exited, the
ledger recorded CANCELLED with `producer == "cancellation"` and no FAILED
attempt, and `checkpoint.pt` was on disk holding the exact resume point
(`round: 1, epoch: 2`).

The resume half could not be reached. `dr_exp retry` refuses a cancelled work
item outright, and even if it did not, attempt 2 would be handed a **different,
empty workspace directory**, so dr-vision could not find the checkpoint it just
wrote. Two dr-exp defects, **D-2** and **D-3** below. No dr-vision defect: every
dr-vision behaviour V3 depends on worked exactly as its contract describes.

### Incident 0 — the workspace had to be cleared before the run

`two_phase_random.yaml` produces the same `work_key` in every campaign, and
attempt workspaces are keyed by `work_key` alone
(`src/dr_exp/config/machine.py:123`), so V1's and V2's completed artifacts were
already sitting in `…/9f02bf2e8e09…9607/attempt-1`. V2's record flagged this as
worth watching. Starting V3 on top of a finished run's `metrics.jsonl` and
`result.json` would have made every V3 assertion ambiguous, so the directory was
archived to
`~/drotherm/data/dr-exp/validation-logs/val-v3/preexisting-workspace-attempt-1/`
and removed before submitting. Recorded as provenance, not filed as a defect —
it is the same cross-campaign workspace sharing V2 already noted.

## Defects

### D-2 (dr-exp) — a cancelled work item can never be retried or resumed

`dr_exp retry` is the only operator path that creates a new attempt, and it
considers only FAILED stage executions:

`src/dr_exp/cli/main.py:466-476`

```python
        failed = [
            stage.execution
            for stage in inspection.work_item_stages(
                engine, work_item_id=item.work_item_id
            )
            if stage.execution.state is StageExecutionState.FAILED
        ]
        if not failed:
            raise click.ClickException(
                f"{item.work_key.value[:12]} has no failed stage to retry"
            )
```

`dr_platform.recovery.retry.retry_stage` enforces the same rule one layer down
(`retry.py:61-64`: `if row["state"] != StageExecutionState.FAILED.value: raise
ValueError("only a FAILED stage execution can be retried")`), so this is not a
CLI-only filter that a flag could widen — the platform primitive would need a
cancelled-eligible path too.

`dr_exp cancel` puts the execution in CANCELLED (`cancel_work` →
`CancellationDisposition.CANCELLED_ADMITTED`), which is terminal and outside
that set. Re-submitting dedupes by `work_key` and does not reopen the item.
The result: **cancel is irreversible**. An operator who pauses a multi-hour job
to free the GPU cannot ever restart it, and the checkpoint dr-exp asked the
trainer to write is unreachable through any dr-exp command.

Repro (about 3 minutes on `mini`):

```
dr_exp --log-level info submit --machine mini --campaign v3repro --run r \
  ~/drotherm/repos/dr-vision/configs/dr_exp/two_phase_random.yaml
dr_exp --log-level info worker --machine mini --campaign v3repro --with-dispatcher &
#   poll the attempt workspace until metrics.jsonl has a `"kind": "round"` record
dr_exp --log-level info cancel --machine mini --campaign v3repro <work_key>
dr_exp --log-level info retry  --machine mini --campaign v3repro <work_key>
#   → exit 1, Error: <work_key> has no failed stage to retry
```

Owner: **dr-exp** (`src/dr_exp/cli/main.py`), with a dependency on
**dr-platform** (`dr_platform/recovery/retry.py`) if the fix is to make
CANCELLED retryable rather than to add a distinct resume command.

### D-3 (dr-exp) — the per-attempt workspace makes the documented resume contract unachievable

The README tells trainers to checkpoint into their workspace so they can
resume (`README.md:138-144`):

> **Artifacts** belong under `request["workspace"]`, which is also the child's
> working directory and survives the run.
> **SIGTERM means checkpoint and exit.** … A trainer that wants to resume
> should checkpoint within that window.

But the workspace handed to the trainer is per **attempt**, not per work item:

`src/dr_exp/config/machine.py:121-123`

```python
    def workspace_for(self, work_key: str, attempt: int) -> Path:
        """Return the per-attempt working directory for one work item."""
        return self.workspace_root / "runs" / work_key / f"attempt-{attempt}"
```

and `src/dr_exp/execution/attempt.py:60-62` passes exactly that path as the
request's `workspace`. Nothing copies, links, or seeds a new attempt's
directory from the previous one — `workspace_for` has only these two callers.
So a trainer that checkpoints where dr-exp tells it to will find that
checkpoint gone on the very next attempt.

This also undercuts the neighbouring at-least-once claim (`README.md:143-144`):
DBOS recovery re-runs the stage body as attempt *n+1*, which likewise gets a
fresh empty directory, so a recovered attempt silently restarts from scratch
rather than resuming. V4 exercises exactly that path and should be expected to
show it.

The per-attempt split is deliberate and pinned by
`tests/unit/test_machine.py:128-132`, so this is a contract conflict to resolve
by decision, not an accidental path bug. The two coherent resolutions are (a)
give the trainer a per-`work_key` durable directory for checkpoints — with the
per-attempt directory kept for attempt-scoped artifacts — or (b) drop the
resume language from the trainer contract and document that every attempt
starts clean. dr-exp currently promises (a) and implements (b).

Evidence that dr-vision holds up its end and only dr-exp's side is missing: the
checkpoint written during this cancellation is complete and correct
(assertion 7 — `round: 1`, `epoch: 2`, model, optimizer, and both RNG states,
plus a `params_hash` guard), and it sits in `attempt-1/`, which attempt 2 would
never read.

Owner: **dr-exp** (`src/dr_exp/config/machine.py:121-123`,
`src/dr_exp/execution/attempt.py:60-62`, `README.md:138-144`).

### Not defects

- **dr-vision.** Everything V3 depends on behaved as its contract states: the
  SIGTERM handler set the stop flag, the runner stopped at an epoch boundary,
  `save_state` wrote a complete checkpoint inside the grace, a `kind: "stopped"`
  record was appended, and `train` returned a strict-JSON result with
  `completed: false` and `stopped_at: {"round": 1, "epoch": 2}` so the child
  exited cleanly rather than being killed. No dr-vision change is needed for
  V3 to pass; D-2 and D-3 are entirely dr-exp's.
- **DBOS cancellation tracebacks in the worker log.** Noisy but correct; see
  the note under assertion 17.
- **Cross-campaign workspace sharing.** Already recorded in V2 and handled here
  as incident 0.

- Round 0's first epoch is again the slowest (3.45 s against a 3.16 s median),
  the same MPS warm-up and dataloader-construction effect V1 and V2 saw, though
  milder here (V1's round 0 first epoch was 5.40 s).
- **Cancellation cost.** The child was gone on the first poll after `cancel`
  returned, i.e. well inside the 30 s `termination_grace_seconds`, despite
  having to serialize an 8.6 MB checkpoint (model, optimizer, and both RNG
  states). SIGKILL was never needed. Checkpointing is not a meaningful drag on
  the shutdown grace at this model size.
