### dr-vision moved between V5 and V6, and again *during* V6

dr-vision was at `e2ff2ac2` when V6 was submitted and is the SHA this run
executed. Track A committed twice around V6, and because dr-vision is installed
**editable**, the second one landed while the job was running. Both are recorded
as provenance; neither is on V6's execution path.

1. **Before V6** — `76eca930` (V5) → `e2ff2ac2`, "Address bot review round 2:
   reject negative seeds at the params boundary". The whole diff is one line in
   `src/dr_vision/params.py`, `seed: int = 0` becoming
   `seed: int = Field(default=0, ge=0)`.
2. **During V6** — `e2ff2ac2` → `4c79aaca`, "Address bot review round 3: bound
   seed to torch's accepted range", adding `_MAX_SEED = 2**64 - 1` and
   `le=_MAX_SEED` to the same `seed` field. `src/dr_vision/params.py` has mtime
   `15:59:04`, inside the attempt window (`15:49:36` → `16:25:44`).

The mid-run edit did not reach this run. The trainer child started at
`15:49:37.484021Z` (the run record's `measurements.started_at`) and imported
`dr_vision.params` during its startup, ten minutes before the file changed;
`python -I` imports the module once, so the process kept the `e2ff2ac2`
content for its whole life. Both edits also only tighten validation of `seed`,
and V6 passes `seed: 0`, which every version accepts identically.

Checked explicitly (`20-drvision-drift.log`): `params.py` is the **only** file
under `src/dr_vision/` modified during the attempt window, and every file on
V6's execution path — `runner.py`, `entry/train.py`, `checkpoint.py`,
`records.py`, `protocols/warm_start.py`, `data/split.py` — has an mtime at or
before `15:13:41`, well before the run.

This is the editable-install hazard V4 and V5 also recorded in milder form
(uncommitted Track A edits, and a SHA that advanced between validations). V6 is
the first where a dr-vision commit landed mid-attempt, so the provenance SHA for
a validation must be the one captured **before** submitting, as it was here
(`00-provenance.log`, written before `03-submit.log`), and not read back
afterwards.

### Assertion 15 — the checkpoint policy was not exercised, and could not be

The plan asks V6 to assert "the latest-only checkpoint policy holds", expecting
"growing checkpoints under the latest-only policy". **No checkpoint file existed
at any point during or after this run.** That is correct behaviour, not a
defect, and V6's 34-round schedule is what makes the reason unambiguous:

- dr-vision writes a checkpoint only on the **stop** path. `run_warm_start`
  calls `save_state` at exactly one site — the `outcome.record is None` branch
  taken when `stop_requested()` returned true at an epoch boundary
  (`dr-vision/src/dr_vision/runner.py:259-265`) — and `entry/train.py:96-111`
  supplies `save_state` solely to serve that path. A round that *finishes*
  appends its `RoundRecord` and moves on without persisting state.
- So checkpoints are not per-round snapshots that accumulate and get pruned to
  the latest. They are a single "where this attempt was cut off" artifact. A run
  that is never cut off writes none, and the number of rounds is irrelevant:
  V6's 34 completed rounds produced exactly as many checkpoints as V1's 2, which
  is zero.
- `entry/train.py:110-111` additionally clears any checkpoint on the completed
  branch, so even a resumed run that finishes leaves none behind.

The policy in effect was confirmed to be `LATEST` (`WarmStartParams`'s field
default; the YAML sets no `checkpoint_policy`) — `01-schedule-and-dataset.log`.
A read-only probe in a throwaway temporary directory (`18-…-probe.log`, which
touched neither dr-vision nor the V6 workspace) confirms what that policy means
for *this* config's round indices: `checkpoint_path(ws, LATEST, r)` resolves to
the single filename `checkpoint.pt` for r = 0, 7, 17 and 33 — one destination
across all 34 rounds — where the `ALL` policy would resolve to four distinct
`checkpoint-round-<r>.pt` files.

That probe is evidence about the policy's destination function, **not** about
V6's live run, so it does not convert assertion 15 into a pass. The live
latest-only behaviour over many rounds — a real batch-online attempt stopped
twice and leaving one `checkpoint.pt` that advances — remains unobserved by
V1–V6. V3 and V4 exercised the write path, but on 2-round two-phase jobs and
with a single stop each, so neither observed a checkpoint being *replaced*.

This refines V1's reading of the same question. V1 recorded "no `checkpoint.pt`
after a successful run is correct per dr-vision's design" and marked its
assertion satisfied. That conclusion is right, but V6 shows the assertion the
plan actually wanted (a growing/pruned checkpoint under a long schedule) is not
reachable from an uninterrupted run at all — the run length was never the
variable. Filed here as a gap in the validation plan, not as a defect in
dr-vision or dr-exp: dr-vision's `.defs/contracts.toml` scopes the policy to
*where an interrupted run's state is written* — `latest` "writes every
checkpoint to `checkpoint.pt`, so one file exists at a time", `all` writes
`checkpoint-round-N.pt` — and states that "an interrupted run always persists
its state". It never promises a checkpoint from a run that is not interrupted,
which is exactly what the code does.

**The per-round time curve.** Round cost is the product of two quantities that
move independently: a subset that grows by a fixed 1000 items per round, and an
epoch count that does not trend. Per-epoch cost tracks subset size almost
perfectly linearly — 0.19 s/epoch at 1000 samples to 6.00 s/epoch at 33333 —
while epochs-to-threshold stay in a band of 9–27 with no drift across the run
(median 18, mean 18.4). The result is a round curve that rises roughly linearly
in trend (2.8 s → 108.2 s) but is visibly noisy round to round, because a round
that happens to need 27 epochs (round 32, 165.2 s) costs more than the larger
final round needing 18 (round 33, 108.2 s).

- **Per-sample-epoch cost is flat at 182 µs.** Median 185.6 µs/(sample·epoch)
  over all 34 rounds, and **182.4 µs** over the 25 rounds with ≥10000 samples.
  This matches V1's ~180 µs and V2's ~180–190 µs solo figures on the same
  hardware, so the batch-online shape introduces no per-sample penalty; it is
  the same MPS throughput applied to a longer schedule.
- **Small rounds are dominated by fixed cost.** Round 0 shows 310 µs/(sample·epoch)
  and round 1 shows 225, decaying to the ~182 plateau by round 6. At 1000
  samples a 128-item batch size means 8 steps per epoch, so per-epoch overhead
  is a large fraction of the epoch.
- **The first epoch of each round is the outlier**, as in V1 and V2 (round 0:
  1.28 s against a 0.19 s median; round 33: 6.13 s against 6.00 s). The
  absolute penalty is roughly constant, so it matters enormously in early
  rounds and is negligible late.
- **Per-round evaluation is not separately visible.** Round seconds equal the
  sum of their epoch seconds to the printed precision at every round, so
  dr-vision's `seconds` field on a round record measures training only; the
  holdout+test evaluation cost falls in the 89 s of non-epoch attempt time.
- **Cost of the long shape.** 2167 s for the batch-online job against ~355 s for
  the two-phase shrink-perturb arm in V2 — about 6x — for 34 rounds instead of 2
  and 625 epochs instead of ~55. On `mini` a full batch-online CIFAR-10 run is a
  ~36-minute job, well inside the 86400 s budget, so the batch-online grids in
  dr-vision's M3 are affordable at this scale.

**Learning curve (a dr-vision observation, recorded but not asserted).** Holdout
accuracy rises from 0.3005 at 1000 samples to 0.7883 at the full pool, with
final test accuracy 0.7825 tracking it closely (the two agree to within 0.01 at
every round, so the 16667-item holdout is a sound proxy for the official test
split). The rise is not monotone: 8 of the 33 round-to-round transitions dip,
the largest by 0.0144 (round 22 → 23). This is expected for a shrink-perturb run
re-initialized every round and trained to a fixed 99% training-accuracy
threshold rather than to convergence, and V6 asserts nothing about it — V6's
job is load, and the warm-start numerics are V2's subject.

## Defects

None found. No new dr-exp, dr-exec, dr-platform, or dr-vision defect is filed
from V6, and none of the defects recorded by V2 (`D-1`) or V3 (`D-2`, `D-3`) is
on V6's path: V6 submits one job once, under a fresh run key, and never
cancels, retries, or restarts a worker.

The one item worth carrying forward is the **plan gap** documented under
"Assertion 15": no validation in V1–V6 observes a checkpoint being *replaced*
under the latest-only policy, and no uninterrupted run can. Closing it needs a
run stopped at least twice at different rounds, with `checkpoint.pt` read
between the stops — a variant of V3/V4 on a many-round schedule, not a variant
of V6.
