## Deviation from the assignment: what "the canary" is

Unchanged from V2, and V2's reasoning is not repeated here. In short: the
assignment directs `dr_exp sweep … canary_sweep.yaml` and then asserts the
three-arm ordering `A ≈ C > B`, but `canary_sweep.yaml` fixes
`shrink: 0.4, perturb: 0.1` and sweeps `seed ∈ {0,1,2}`, so all three of its
points are arm C and the ordering is not evaluable against it. Its own header
and dr-vision's plan both define the canary as the three job files at one seed.
The canary was therefore run as three `submit` calls into one campaign, which
leaves every dr-exp assertion V2 asks for intact.

## Three run keys, and why they are new

V2 used three run keys because a second `submit` under one run key was silently
discarded (V2's defect D-1). That is now a hard error rather than a misreport,
but the shape is the same: one run key registers one submission.

The keys are `v2b-`-prefixed rather than V2's `canary*` keys because run keys
are globally unique in `platform_pipeline_runs`, not campaign-scoped. Reusing
them under the new campaign failed cleanly with exit 1:

```
Error: run key is already bound to different immutable provenance: 'canary'
```

This is correct, intended dr-platform behaviour (a run key names an immutable
registration) and the message states the cause. It is the same convention V3b
used (`v3b`/`v3c` rather than reusing `v3`). Not a defect; recorded as incident
2 in the experiment log, log `submit-runkey-collision.log`.

## What changed against V2, and why

Per-arm comparison (`v2-vs-v2b.log`):

| Arm | V2 r0 | V2b r0 | V2 r1 epochs | V2b r1 epochs |
|---|---|---|---|---|
| A random | 22 ep, holdout 0.693346 | 22 ep, holdout 0.695086 | 33 | 35 |
| B warm | 22 ep, holdout 0.695086 | 22 ep, holdout 0.695086 | 27 | 27 |
| C shrink-perturb | 27 ep, holdout 0.715546 | 22 ep, holdout 0.695086 | 34 | 31 |

Arm B is bit-identical across both runs, as V2's erratum predicted for the
`(1, 0)` arm. **Arm A is not**, though the erratum predicted it would be, and
the reason is worth recording because it corrects that erratum: at `738bfc3`,
round 0 called `build_model` to construct the `fresh` model even for arm A,
where the `(0, 1)` transform makes the combination mathematically equal to that
fresh model. `76eca93` skips the call entirely, so the global RNG stream
entering round 1 is one `build_model` draw shorter and arm A's round-1
re-initialization draws different weights. The erratum's claim was about the
*transform* being the identity — true — but it did not account for the *RNG
consumption* of the skipped call. The consequence is bounded: arm A moved from
33 to 35 round-1 epochs, the direction check is unaffected, and Check 2 now
passes with a 4-epoch margin rather than a 1-epoch inversion.

This is a dr-vision observation, not a dr-exp defect, and it does not change
either repository's verdict. It is recorded so the two canary logs can be read
against each other without the discrepancy in arm A looking unexplained.

## Defects

**None found in this run.** V2's two findings are both resolved or reclassified:

- **D-1** (a second `submit` under an existing run key silently discarded while
  reporting success) is fixed in dr-exp `a71fe79` by
  `_require_membership_registered` (defined at `src/dr_exp/platform/submission.py:114`, called at `:87`),
  which reads the run's members back and raises instead of misreporting. This
  rerun used three distinct run keys from the start and so did not re-trigger
  the original path; the fix's behaviour is covered by the CLI test added with
  it, and the adjacent run-key immutability error surfaced correctly here with
  exit 1 (see "Three run keys" above).
- **D-2 as V2 filed it** (worker `--campaign` does not scope admission) did not
  recur, because no other campaign had non-terminal work when this run started
  — every work item in `dr_exp_dev` outside `val-v2b` was already `succeeded`
  or `cancelled`. The behaviour V2 observed is unchanged; this run simply did
  not exercise it. Note that "D-2" in the Track C decisions refers to a
  different item (cancellation being terminal, validated in V3b); V2's D-2
  numbering is local to that record.

The V2 finding filed under "Not defects" as *workspace reuse across campaigns*
is now closed by **D-3**: assertion 18 shows workspaces keyed by
`(campaign_key, work_key)`, so a re-used config in a new campaign no longer
overwrites an earlier campaign's artifacts in place. V2 needed a pre-run
cleanup for exactly that hazard; this run needed none.
