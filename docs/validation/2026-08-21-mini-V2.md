## Deviation from the assignment: what "the canary" is

The assignment directs `dr_exp sweep … configs/dr_exp/canary_sweep.yaml` and
then asserts the three-arm ordering `A ≈ C > B`. Those two instructions are
inconsistent, because `canary_sweep.yaml` is not the canary: it fixes
`shrink: 0.4, perturb: 0.1` in `base.params` and sweeps `seed ∈ {0,1,2}`, so
all three of its points are arm C. Its own header says the canary
"is deliberately NOT a sweep … Submit the three job files", and dr-vision's
plan (`warm-start-reimplementation.md`, "Canary") defines it as the three job
files at one seed.

The canary was therefore run as dr-vision defines it — three `dr_exp submit`
calls into campaign `val-v2` — which keeps the dr-vision acceptance check
evaluable and leaves every dr-exp assertion V2 asks for intact (three distinct
`work_key`s in one campaign, `train-mps` routing, capacity behaviour with
`--max-jobs 3`, dispatcher sweep health).

## Defects

### D-1 — a second `submit` under an existing run key is silently discarded (dr-exp)

**Owner: dr-exp.** Severity: high — it silently drops submitted work while
reporting success, so a user believes N jobs are queued when 1 is.

Submitting three different configs under one `--run` key reports success three
times and registers only the first:

```
$ dr_exp --log-level info submit --machine mini --campaign repro-runkey --run r1 .../two_phase_random.yaml
Submitted run r1 to campaign repro-runkey: 1 member(s), 1 new, 0 reused
  9f02bf2e8e09
$ dr_exp --log-level info submit --machine mini --campaign repro-runkey --run r1 .../two_phase_warm.yaml
Submitted run r1 to campaign repro-runkey: 1 member(s), 1 new, 0 reused
  5e58f4e1bb93          <-- reported, never registered
$ psql -d dr_exp_dev -c "select work_item_id, origin_run_key, left(work_key,12) from platform_work_items where campaign_key='repro-runkey';"
 13 | r1 | 9f02bf2e8e09      <-- one row
```

**Mechanism.** The first submit closes the run: `platform_pipeline_runs` gets
`registration_closed_at` set with `expected_member_count = 1`. dr-platform
enforces run immutability at the schema level, so the later submits are
replayed against the closed run idempotently and register nothing — correct
behaviour on dr-platform's side. The misreport is dr-exp's: in
`src/dr_exp/platform/submission.py:84-87`, `SubmissionResult.work_keys` is
built from the **locally constructed** `members` list rather than from the
receipt dr-platform returned:

```python
return SubmissionResult(
    receipt=receipt,
    work_keys=tuple(member.work.work_key.value for member in members),
)
```

`src/dr_exp/cli/main.py:289-297` then prints the receipt's counts (which
describe the *original* run: "1 member(s), 1 new, 0 reused") above
`result.work_keys` (which describes the *rejected* input). The two halves of
the message come from different sources, and the combination reads as a
successful new submission.

**Controls** (both in `defect-control.log`, confirming the diagnosis is
specific and dr-platform is behaving):

- Distinct run keys, same campaign → both items register (13 under `r1`,
  14 under `r2`).
- One `sweep` with 3 grid points under a single run key → all 3 register
  (`3 member(s), 3 new, 0 reused`, three rows). Multi-member registration in
  one call is fine; it is only the *second call* that is lost.

**Repro:** `defect-repro.log`. Two `dr_exp submit` calls with different config
files, same `--campaign` and same `--run`, then read `platform_work_items`.

**Not fixed here** — V2 is a validation run and dr-exp source changes are out
of its scope. Worked around by giving each arm its own run key.

### D-2 — worker `--campaign` does not scope admission (dr-exp, behaviour note)

**Owner: dr-exp.** Severity: medium; arguably by design, but the CLI surface is
misleading.

`dr_exp worker --machine mini --campaign val-v2` admitted and ran jobs from
campaigns `repro-runkey` and `repro-sweep`. The dispatcher's admission query is
global, ordered by `(priority, rank)` with no campaign predicate — visible in
the ledger index `platform_ix_stage_executions_ready_admission btree
(stage_key, priority, rank) WHERE state = 'ready'`. Because `rank` is a large
hash-like integer, ordering across campaigns is effectively arbitrary, so an
unrelated campaign's READY work can preempt the campaign named on the command
line.

Observed directly: with three `val-v2` items READY and five repro items READY,
the first admission pass ran two repro items (`admitted=2
skipped_capacity=6`) while all three `val-v2` items stayed READY.

This is defensible as a design (one worker drains a machine's queues, not one
campaign), but then `--campaign` on `worker` promises scoping it does not
deliver. Either it should filter admission, or it should be documented as
affecting only which campaign's work the worker reports on. Recorded as a
finding for dr-exp to decide; no change made here.

**Repro:** submit work to two campaigns, run `dr_exp worker --campaign A`,
observe items from campaign B admitted (`worker.log` from the first start,
preserved in the incident notes of the experiment log).

### Not defects

- **`canary_sweep.yaml` is not the three-arm canary.** The file is correct and
  self-documenting; the V2 assignment misreads it. See "Deviation" above.
- **dr-vision's checkpoint/params guard.** `CheckpointMismatchError` correctly
  refuses a checkpoint written for different params. It does not fire when the
  params are identical — correct for a retry, and the reason incident 4 in the
  experiment log had to be handled by clearing the stale workspace rather than
  relying on the guard.
- **Workspace reuse across campaigns.** Attempt workspaces are keyed by
  `work_key` alone (`src/dr_exp/config/machine.py:123`), so the same config in
  two campaigns shares a directory. This is consistent with `work_key` being
  the identity of a unit of work, but it means a re-used config can overwrite
  an earlier campaign's artifacts in place. Worth noting for later validations
  (V5 re-submits the V2 configs); not filed as a defect because no contract
  claims per-campaign workspaces.

## Throughput observations

Full tables in the experiment log, section 5.

| Arm | Round 1 median (s/epoch) | Concurrency during round 1 | Job wall time (s) |
|---|---|---|---|
| A random | 6.10 | alone | 281.6 |
| B warm | 7.50 | 2-wide | 293.1 |
| C shrink-perturb | 7.35 | 2-wide, then alone | 355.1 |

- **Single vs. 2-wide per-epoch cost.** Arm A ran alone and matches V1's solo
  rate almost exactly (6.10 s vs V1's 6.11 s at the same 33333-sample subset),
  making it a sound single-job reference. Arms B and C at 2-wide ran 7.50 and
  7.35 s/epoch — a **20–23% per-epoch slowdown for 2x aggregate throughput**,
  so concurrency 2 is a clear makespan win on `mini`.
- **Makespan.** Three jobs completed in 569 s wall clock (18:46:17 → 18:55:54
  UTC) against 930 s of summed job duration.
- **Per-sample cost** is stable across subset sizes solo: ~0.19 ms/sample/epoch
  at 16666 and ~0.18 at 33333, matching V1.
- **First epoch of each round is the slowest** for every arm (MPS warm-up plus
  dataloader construction), most pronounced in round 0.
- These are the first concurrency-2 numbers; together with V1's solo baseline
  they are the initial input for `dr-vision/docs/infra/mini-throughput.md`.
